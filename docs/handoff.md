# Handoff

Canonical shared context for every coding agent on CraftCV. Read this before starting and update it before finishing. Keep it current rather than appending a chronological log.

## Product direction

CraftCV is a local-first Electron workspace that turns a user's existing CV and source projects into evidence-backed, tailored applications. A parent folder such as `kaira`, `omakala`, or `logset` is one project; nested Git repositories are its services. AI analysis belongs to the selected project as a whole, not to each repository and not to inferred name-prefix groups.

The product should feel like a focused desktop document workspace: a shared shell, compact controls, plain-language errors, and a Google Docs-style local editor with formatting, headings, lists, links, tables, undo/redo, autosave, and PDF/DOCX export. Do not add user-contribution claims that cannot be supported by repository or CV evidence.

## Current state

- The renderer is feature-based: `src/renderer/app` owns the shell; `common` owns shared API, state, and UI; `features` owns AI, documents, library, projects, settings, and workspace behavior. See `docs/architecture.md` before moving boundaries.
- The main process is a layered backend: IPC routes validate and delegate, services coordinate workflows, domain modules hold pure rules, and storage/scanning/AI/documents modules perform I/O.
- The UI uses HeroUI v3, Tailwind CSS v4, and Iconify, in HeroUI's own font (its `--font-sans` system stack; Inter and `@fontsource/inter` were removed 2026-11-03). Headings and paragraphs are HeroUI `Typography.Heading`/`Typography.Paragraph` (size `sm`); `styles.css` tunes `.typography--h1`–`h4` to the app's denser scale, body line height to 1.6, and makes default-coloured Typography inherit its surroundings' colour (`color="muted"` still applies). Prefer Typography over raw `h1`–`h4`/`p` in new UI. It has a floating sidebar (CraftCV.s floating sidebar implemented in CSS: `--sidebar-inset`, `--sidebar-width` 240px, `--sidebar-width-collapsed` 56px, `data-state` on `.sidebar`; ⌘B/Ctrl+B toggles it except while typing, since ⌘B is bold in the editor), a sticky translucent header (`--topbar-height` 56px) with breadcrumbs, persisted light/dark theme, HeroUI toasts for errors and notices (top; errors stay until dismissed or the next action, notices close after 6 seconds; error toasts can carry provider-page buttons), and a short Hairline-based startup screen.
- The shared product styling was polished on 2026-11-03: functional page titles, restrained cyan state color, compact controls, and HeroUI remain the common vocabulary. The five-step application flow is deliberately flat: one 820 px reading column, a compact progress row, plain headings and footers, and hairlines instead of a large workflow card. HeroUI components keep their supported library styling; custom CSS is reserved for CraftCV-owned layout wrappers. `DESIGN.md` records the current patterns.
- `build/icon.svg` is the CraftCV logo source (redesigned 2026-11-03: a cyan C holding a CV page whose one cyan line is the tailored line, on the dark tile). The renderer, launch screen, packaged app, development Dock icon, and development window icon use it or its generated PNG. Regenerate `build/icon.png` (1024px, transparent corners) by rendering the SVG with Electron; run Electron with `ELECTRON_RUN_AS_NODE` unset, since VS Code's terminal sets it. The expanded sidebar shows the version beside the name (`__APP_VERSION__`, defined from `package.json` in `electron.vite.config.ts` and `vitest.config.ts`, declared in `src/renderer/globals.d.ts`); collapsed, the brand link fills the rail so the logo centres over the icons.
- Settings supports ChatGPT-plan sign-in plus OpenAI and Anthropic API keys. Anthropic Pro/Max credentials are intentionally unsupported. Provider setup links and ChatGPT limit actions open only allow-listed external pages.
- AI/provider failures are translated into human-readable, optionally actionable errors. Streaming replies tolerate nullable fields seen in ChatGPT-plan events.
- Structured AI replies accept conservative wrappers some models add (a JSON code fence, a short preface, or a JSON-encoded string) but still must pass the requested Zod schema. Provider output-limit responses are detected separately and explained as cut off. Project understanding requests ask for concise service descriptions and allow up to 6,000 output tokens.
- A new application is one step per page (`step` in the workspace store, one route so the sidebar link stays active): step 1 builds the context (a 760px column); Analyze switches to step 2, which shows the loader with a Cancel button and then the suggestions, and returns to step 1 if the analysis fails. "Edit context" and "Back to suggestions" move between them; opening a past session lands on step 2.
- Project cards are compact when collapsed. Expanding the path reveals repositories as a real folder tree beneath the imported project root; names are never synthetically grouped.
- Project understanding is generated for the selected project, summarizing its architecture, technologies, and service map across the nested repositories.
- The job description can be imported from a link (`JobLinkField` above the job textarea). The main process reads Greenhouse, Lever, Ashby, Workday, SmartRecruiters and Workable jobs from their public APIs (each checked against a live reply on 2026-11-03); other pages from their schema.org `JobPosting` (JSON-LD, then microdata); Indeed and LinkedIn from their own layout; and otherwise the page's main text, which the notice asks the person to check. Indeed search and tracking links (`vjk`, `jk`) become `/viewjob?jk=…`. Pure parsing is in `src/main/domain/job-posting.ts`, network rules and the shared `pageJob` in `src/main/jobs/job-link.ts`.
- The wizard's step row is `src/renderer/common/ui/Stepper.tsx`, CraftCV.s semantic compound Stepper, implemented with project-owned code and HeroUI v3 tokens. It is controlled by the current step; steps not yet reachable are disabled, and below 1000px only reached steps keep their titles.
- First run (`src/renderer/features/onboarding/`): a one-time welcome replaces the wizard on a new install (no CVs, projects or applications, and `craftcv-welcomed` not in `localStorage`). **Get started** leads to the wizard with a setup checklist (CV, project folder, optional AI, first application), worked out from the dashboard, never stored; **Skip** also hides the checklist (`craftcv-setup-hidden`). The checklist also shows in the Applications empty state. Until the first application, the Job step offers **Try a sample job** (`sample-job.ts`, a made-up Brightwave posting). ProjectPicker explains project folders when there are none. Settings → Getting started → **Show welcome and setup again** (`replayOnboarding`) clears both flags and sets an in-memory `replay`, so the welcome shows even with work saved; finishing or skipping it ends the replay. `npm run dev:onboarding` (`electron-vite dev --mode onboarding`) starts every launch as a first run, without touching saved data. The core and folder integration flows press Get started / Skip first; `tests/workspace.test.tsx` marks the welcome seen.
- Indeed (401) and Glassdoor (403) refuse plain requests. After a failed import, **Open the posting** loads the link last tried in a separate window (`src/main/jobs/job-page.ts`): in-memory `craftcv-job-page` session, sandboxed, no preload, permissions and downloads denied, https navigation only, new windows kept in the same window. The person signs in if needed, then presses **Use this page** in the main window; the main process reads the DOM from an isolated world and runs `pageJob`. The renderer never sends an address: `openJobPage`, `useJobPage` and `closeJobPage` take no arguments.
- PDF CVs import with their layout (`src/main/documents/pdf-layout.ts`, fed by `readPdf` in the document worker). From where pdf.js places text it rebuilds lines, joins wrapped lines into paragraphs and bullet items, makes larger bold lines (and short bold all-capital lines) headings, keeps centring, bold, italic and links, turns far-apart text on one line (a right-aligned date) into `|`, and turns thin strokes across most of the page into horizontal rules. Font names come from `fontExtraProperties: true`. If the result fails document validation, the import falls back to plain text. DOCX and Markdown still import as plain lines.
- A new application is a five-step wizard on `/` (`src/renderer/features/workspace/steps/`, state in the workspace store, `step` saved on the application so it resumes from the tracker). Step 1 creates an `Application` (`src/main/services/applications.ts`, `src/main/storage/application-store.ts`) with the job's role, company and location guessed (`guessJobDetails` in `src/main/domain/job-analysis.ts`) and no analysis. Step 2 (no page title) shows those details to confirm and the job description as plain text. **View posting** and **Analyse the job** sit beside the "Job description" heading; Analyse opens the AI panel (provider, model, consent) just below it; only then are requirements, keywords and responsibilities shown (`src/main/ai/job-analysis.ts`, keeping only terms the job text names). While the AI runs, a live trace shows each stage (`AnalysisTrace.tsx`): connect, send, the reply streaming in (role, company and terms appear as they are written; terms the job never names and the term still being typed are held back by `draftFrom`), the check against the posting (with what was left out), and saving; Stop cancels it. All three providers now stream when `requestStructured` is given `onText` (OpenAI Responses SSE, Anthropic Messages SSE); `parsePartialJson` reads the unfinished reply. Stages travel on `craftcv:jobAnalysis` (`onJobAnalysis` in the bridge, `BRIDGE_VERSION` 10). The trace uses CraftCV-owned progress primitives in `src/renderer/common/ui/`. It shows real stages and the streamed answer, not the model's hidden reasoning, which providers do not expose. The on-device requirement matcher was removed at the user's request (2026-11-03: complicated and often inaccurate); a changed description clears the analysis, and older applications' on-device analyses are no longer shown. CV and project choices save to the application as they change. Step 5 is still the existing evidence review; Mark as applied moves the card. The Applications page (`/applications`, `src/renderer/features/applications/`) has a List | Board toggle, remembered per device (`craftcv-applications-view`, list by default). The list is a HeroUI `Table` with a status `Select` per row (`keyboardNavigationBehavior="tab"` so the controls are reachable). The board is `src/renderer/common/ui/Kanban.tsx`, CraftCV.s accessible Kanban, implemented with project-owned code, built on react-aria-components' `GridList` + `useDragAndDrop` (react-aria-components 1.22.1, already installed by HeroUI, is now a direct dependency). Cards move between columns by pointer, or by keyboard from the drag handle that shows on focus; a card's position within a column is not kept (no order field), so only drops onto a column are accepted. The board scrolls sideways in a horizontal HeroUI `ScrollShadow` and each column's cards in a vertical one (`Kanban.ScrollShadow`, max `--kanban-column-height` 480px), so edges with more beyond fade out. Pressing a card opens its application, and each card's menu still offers Move to…. Both views share `ApplicationActions` (Continue/Open, open posting, remove with confirmation) and Earlier analyses for sessions without an application. Past sessions left the sidebar. Job links open by application id; the stored URL is checked again with `parseJobLink`.
- Documents are laid out on A4 pages. The document root carries an optional page layout (`margins`, `lineHeight`, `blockSpacing`, `listIndent`, `fontSize`; see `pageLayout`/`layoutStyle` in `src/shared/document.ts`), and a top-level `pageBreak` block starts a new page. PDF import measures the layout from the source, adds a page break at each source page boundary, keeps text sizes, and inserts blank lines for vertical gaps. With `blockSpacing` set the document is in exact mode (`data-layout='exact'`): no editor spacing of its own, so it keeps the PDF's rhythm. The editor (`src/renderer/features/documents/editor/pages.ts`) draws separate A4 sheets and paginates automatically by measuring blocks and inserting gap decorations; gaps are never stored. PDF export prints with the document's margins and CSS; DOCX export uses its margins, line spacing, list indent, body size and `pageBreakBefore`.
- The document editor's chrome is two slim rows: a 45px header (back, title with its save state inline, Save/PDF/DOCX) and a 35px single-row toolbar with 28px controls. The old view bar is gone; zoom lives in the 29px status bar at the bottom.
- The editor and CV import/export flows are implemented. The preload API is versioned by `BRIDGE_VERSION` in `src/shared/runtime.ts`.

## Open items

- **ChatGPT plan reset time.** When a ChatGPT plan hits its usage limit, the error toast reads "Your limit resets soon" because the reply carried neither `resets_at` nor `resets_in_seconds`, the field names OpenAI's Codex CLI uses. The real field in the `response.failed` stream event is unconfirmed. Capture one event and update `src/main/ai/provider-errors.ts`.
- **"Electron" in the macOS menu bar in development.** Unpackaged runs take the app name from Electron's own bundle; it cannot be changed at runtime. Packaged builds show "CraftCV".
- **Dock icon size.** `build/icon.png` fills almost its whole square; macOS icons usually leave about a 10% margin, so it may look large in the Dock. Undecided whether to add padding.
- **LinkedIn job import is fragile.** It depends on LinkedIn serving its public job page to a signed-out request and on its CSS class names (`show-more-less-html__markup`, `top-card-layout__title`, `topcard__org-name-link`, `topcard__flavor--bullet`). LinkedIn's terms forbid automated access; CraftCV makes one request only when the person imports a link, without cookies. If LinkedIn changes the page, the person sees the sign-in message and pastes the text.
- **Job pages that render with JavaScript** (some Workday sites) have no posting in their HTML and fall back to page text or "No job description found". A hidden BrowserWindow could read them; not built.
- **DOCX import is plain text.** `mammoth.extractRawText` drops headings, bold and lists. `mammoth.convertToHtml` plus a small HTML-to-document converter would bring it up to the PDF import.
- **PDF layout heuristics** are tuned on single-column CVs from Google Docs/Chrome. Two-column layouts, tables and scanned PDFs are not reconstructed; a sidebar column's text will interleave with the main column.
- **Pagination limits.** A block taller than a page (a long table) is not split and overflows its sheet; the editor's and Word's line breaking can differ slightly, so a Word export may break pages a line earlier or later. Existing documents without a layout keep the editor's default spacing, now also paginated.
- **Test scripts that edit a document** must save before `app.close()`: the unsaved-changes guard in `src/renderer/app/window-events.ts` holds the window open otherwise.
- **DNS rebinding.** Job links are checked for private addresses before each request and each redirect, but `fetch` resolves the name again, so a hostile DNS server could still point the second lookup at a private address. Pinning the address needs an undici dispatcher.

## Decisions

- **No "Claude plan" provider.** Anthropic does not permit third-party apps to offer Claude.ai sign-in or use Pro/Max credentials (code.claude.com/docs/en/legal-and-compliance). The Anthropic card uses an API key and says a Pro or Max plan does not include API use.
- **External pages by name only.** The renderer asks the main process to open an `ExternalPage` name (`src/shared/contracts.ts`); the URLs are fixed in `src/main/core/external-pages.ts`. Never pass a URL over IPC.
- **Errors for people.** Provider and system errors are translated in the main process (`src/main/ai/provider-errors.ts`, `src/main/ipc/handle.ts`). A message may be `Title\nWhat to do`; the toast shows the first line as its title. An `ActionableError` adds page buttons to the toast (`src/renderer/app/layout/Toasts.tsx`). The store's `error` and `notice` stay the source of truth; the toasts mirror them.
- **Repository tree.** Project cards show repositories by their real folders under the project root, collapsed under the path line. No grouping by name.
- **Job links are fetched by the main process, never the renderer.** Only https on the default port; no credentials in the URL; every address, including each redirect's, must be public; no cookies; 20-second timeout; at most 3 MiB read. Job-board APIs come first because their data is clean. A job read from page text is flagged `fromPage` so the person checks it. The URL comes from the person, which is why this does not go through the `ExternalPage` allow-list.
- **Bridge version.** Bump `BRIDGE_VERSION` in `src/shared/runtime.ts` whenever the preload API changes; a running `npm run dev` must then be restarted.
